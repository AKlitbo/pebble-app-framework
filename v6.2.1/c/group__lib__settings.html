Detailed Description

Loads, saves, and syncs a face's settings from its field table.

A face hands it a field table, and it handles persist and the phone sync without naming any single setting itself.

Definition settings.h:125

Sets a schema's settings struct, its size, and the size it first shipped at, for a schema's initializer.

It fills in .blob, .blob_size, and .first_size. The first size is the struct's size in bytes in the first release that saved it, and it never changes after that release. A saved blob smaller than it cannot be this schema's. One from the first size up to today's size reads in, and every field appended since keeps its default. The struct's sizeof rises with each appended field and would turn away every older save, so the first size has to be written as the number itself, or a macro that is one. The build stops on sizeof, SETTINGS_BLOB_SIZE, a sum, brackets, or a cast written in place, and on a first size of 0 or one bigger than the struct. A constant worked out from sizeof somewhere else, such as an enum, still gets through.

◆ SETTINGS_BLOB_SIZE

#define SETTINGS_BLOB_SIZE ( blob)

(sizeof(blob) + 0 * sizeof(struct { \

The size of a settings struct, and a build that stops when the struct is too big to save. SETTINGS_BLOB uses it for a schema's blob_size.

One persist key holds at most 256 bytes, and the watch saves only the first 256 bytes of a longer write. The fields past that would come back as their defaults on every launch. This stops the build instead, so a face with more than 256 bytes of settings moves some into a companion schema. settings_init logs an error at launch for a schema whose blob_size was filled in without it.

◆ SETTINGS_COUNT

#define SETTINGS_COUNT ( key)
Value:
SETTINGS_COUNT_##key

How many choices the settings page offers on a message key, worked out by the build.

◆ SettingsSchema

typedef struct SettingsSchema SettingsSchema

A face's persistence identity.

Its storage key, current schema version, the face struct to load into (its first byte must be the uint8_t version), that struct's size and the size it first shipped at, the field table that drives defaults/sanitize/serialization, and an optional migration hook to rescue pre-versioned data. SETTINGS_BLOB fills in the struct and both sizes.

A face can persist more than one struct by chaining schemas through companion: each schema points to the next and the last one is NULL. settings_init walks the chain so load, save, serialize, and inbox decode all cover every schema. Each link owns its own key, version, and blob, so a domain (e.g. weather or a colour table) can sit in its own key instead of bloating the main one. The typed reads (settings_u8/str) index the whole chain and remember each field's owning schema, so a shared field (id < SETTING_COUNT) can live in any link. A face built with a plugin define also gets the framework's own schema, on SETTINGS_PLUGIN_SOURCE_KEY. It is never linked onto the face's chain. The walk in settings_chain.h visits it after the face's last schema.

◆ settings_init()

void settings_init ( const SettingsSchema * schema)

Load a face's settings from their saved blobs, applying defaults first.

Walks the companion chain so every schema in it is loaded. A saved blob is read only when its size and version fit the schema, or when the schema's migrate hook takes it, and every field read back is cleaned. A blob that fits neither is dropped and the schema stays on its defaults. A schema over the 256 bytes one persist key holds is logged as an error, since it can never be saved whole. SETTINGS_BLOB stops the build for one, so the log catches a schema written without it.

A face built with PLUGIN_WEATHER, PLUGIN_CALENDAR, or PLUGIN_STOCKS that declares the kind's select key also gets the framework's schema for the source choice, walked after its own and saved under SETTINGS_PLUGIN_SOURCE_KEY. The choice is only kept once this has run, so a face with no settings of its own still has to call it, as settings_init(NULL), or a reset of the Pebble app drops the wearer's pick. The pick only reaches the phone in the settings reply, so the build adds SETTINGS_REQUEST and SETTINGS_FRESH to such a face's keys. Call it before appmessage_open, which sizes the outbox from the settings reply. Called after, every settings reply goes out empty and a reinstall restores nothing. A face schema on SETTINGS_PLUGIN_SOURCE_KEY is logged as an error and the framework's schema is left out. A face field on a select key the framework keeps is logged too.

Parameters
schemaThe head schema defining the face's settings, or NULL for a face with none.
