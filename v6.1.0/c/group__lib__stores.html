Store tags

Every store stamps the first byte of its blob with a tag. The high nibble names the store and the low nibble is that store's layout revision.

The size on its own cannot tell two blobs apart. Reordering two fields keeps the size, and so can two different structs, so the tag is what makes the guard mean anything. Bump a store's low nibble whenever its persisted struct changes shape, and an older blob is dropped rather than read as the wrong thing.

#define STORE_TAG_WEATHER   0x13
 The weather store's blob.
#define STORE_TAG_STOCK   0x21
 The stock store's blob.
#define STORE_TAG_CALENDAR   0x31
 The calendar store's snapshot.
#define STORE_TAG_HEALTH   0x42
 The health store's saved heart rate window.
#define STORE_TAG_LOCATION   0x51
 The location store's last fix.
#define STORE_TAG_HRV   0x61
 The health store's saved HRV readings.

Detailed Description

Weather, health, calendar, stocks, and the other readings a face shows.

Each store keeps its reading fresh and nudges the screen when it changes.

◆ HEALTH_HR_SENSOR

#define HEALTH_HR_SENSOR   0

1 on a platform where a watch model carries a heart rate sensor, 0 everywhere else.

The platform is the only thing that tells. The health service never checks for the sensor itself, so health_service_metric_accessible for the heart rate gives a watch built without one the same answers as a watch with one. In PebbleOS, fw/applib/health_service.c returns NotSupported only for a time range or aggregation it cannot answer, and NoPermission only for the wearer's heart rate setting. The emulator's setting is always on (fw/shell/sdk/prefs.c), so it reports a heart rate as there on gabbro. The boards that build the sensor in, with CONFIG_HRM in their defconfig, are obelix, the Pebble Time 2 on emery, and qemu_emery. Asterix on flint and getafix on gabbro have none.

Diorite is in because the Pebble 2 HR has a sensor. The Pebble 2 SE on the same platform has none, and the health service cannot tell the two apart, so its heart rate slot shows dashes.

A new platform with a sensor joins the list here.

◆ store_fetch_reconfigure()

time_t now,
bool empty )

What a store's reconfigure does with its polling.

Switching the store off clears the live flag, which stops the cadence turn too, and drops any fetch still waiting. A store that init started with live false stays off whatever live says, so a settings save never starts a store seeded for screenshots fetching over its fixture. A store whose init never ran ignores the reconfigure altogether.

A store that keeps polling keeps its launch fetch, since a settings push that lands in the first second would otherwise cancel it and leave a restored reading stale until the next deadline.

An empty store has nothing to draw, so it catches up right away. One that already holds data waits for its deadline, so a save that only touched colours does not fetch on the spot and spend a metered provider's quota. That deadline is a wall-clock boundary, so a save can bring it nearer but never past the interval's rate.

Parameters

poll_minMinutes between polls. 0 or less means no polling.
liveTrue on a live face. A store init started not live stays not live.
nowThe current wall-clock time.
emptyTrue when the store holds nothing to show yet.

◆ store_poll_start()

Take a store's interval and whether it is live, as its init does.

Init is the one place that decides whether the store is live at all. A store it starts with live false is pinned, and stays not live through every reconfigure, as store_poll_set covers. A store whose init calls store_poll_set instead is never pinned, so a reconfigure can turn it live.
